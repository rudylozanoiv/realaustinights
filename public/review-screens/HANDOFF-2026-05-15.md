## 1. Live blocker — code-side root cause CONFIRMED

The repo has **NO mechanism** to create `public.users` (or `public.profiles`) rows. This fully explains the observed state where all three test accounts (Gmail / Proton / iCloud) have auth.users rows with `email_confirmed=true` but `public_users_email_row_count=0`.

| Probe | Result |
|---|---|
| `from('users')` / `from('profiles')` anywhere | 0 matches |
| SQL files / migrations folder / `supabase/` dir | none exist |
| `handle_new_user`, `on_auth_user_created` strings | 0 matches |
| `ensureProfile`, `upsertProfile`, RPCs | 0 matches |
| `app/auth/callback/route.ts` | only `exchangeCodeForSession` — no DB insert |
| `app/auth/confirm/route.ts` | only `verifyOtp` / `exchangeCodeForSession` — no DB insert |
| `components/signup-modal.tsx` | `supabase.auth.signUp({ data: { instagram } })` — Instagram lands in `auth.users.raw_user_meta_data`, not `public.users` |

### What this means
The row-creation path does not exist in code, AND no SQL migration in this repo defines a trigger. If a Supabase database trigger was set up via dashboard, it is either missing or silently failing — but the repo itself cannot tell us. **Verify in the Supabase dashboard.**

### Two viable paths (pick one — do not do both)

**A. Database trigger (preferred — keeps `auth.users` as source of truth)**
- Run SQL in Supabase SQL Editor:
  ```sql
  create or replace function public.handle_new_user()
  returns trigger language plpgsql security definer as $$
  begin
    insert into public.users (id, email, created_at)
    values (new.id, new.email, now())
    on conflict (id) do nothing;
    return new;
  end; $$;

  drop trigger if exists on_auth_user_created on auth.users;
  create trigger on_auth_user_created
    after insert on auth.users
    for each row execute function public.handle_new_user();
  ```
- Then backfill the 3 existing test users:
  ```sql
  insert into public.users (id, email, created_at)
  select id, email, created_at from auth.users
  on conflict (id) do nothing;
  ```
- Pro: clean. Con: lives outside the repo — invisible to git.

**B. App-side insert in callback route**
- Patch `app/auth/callback/route.ts` after `exchangeCodeForSession` succeeds:
  ```ts
  const { data: { user } } = await supabase.auth.getUser();
  if (user) {
    await supabase.from('users').upsert({
      id: user.id,
      email: user.email,
      created_at: new Date().toISOString(),
    }, { onConflict: 'id' });
  }
  ```
- Requires RLS policy: `authenticated` role can insert their own row.
- Pro: visible in git, version-controlled. Con: runs on every callback (idempotent via upsert).
